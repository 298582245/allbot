# 开发者接口与 MCP 规划

## 1. 目标与范围

开发者接口和 MCP 是两种面向外部调用方的接入方式，底层身份、应用凭证、权限校验、业务能力和审计必须共用。先建立应用授权与业务服务层，再分别提供 HTTP 开发者接口和 MCP 协议适配器。

这里的“开发者接口”指供外部程序调用 AllBot 管理能力的正式接口，不是 `openapis/` 下用户自定义脚本形式的 OpenAPI。现有自定义 OpenAPI 的目录、Token、脚本运行时和调用方式保持独立，不自动获得新应用权限，也不纳入首期迁移。

授权目标覆盖管理员后台的业务功能，不限于插件。应用获授哪些模块，就能通过开发者接口及 MCP 调用该模块下所有已开放接口；未授权模块、尚未实现或已停用的接口默认不可调用。

## 2. 设计原则

1. **一个安全主体**：每个后台创建的应用拥有唯一 `appKey` 和一个当前有效的 `appSecret`；开发者接口与 MCP 识别同一个应用。
2. **协议适配器薄化**：HTTP 与 MCP 只负责解析协议、认证和格式化响应；业务授权和业务执行调用同一服务层。
3. **按模块授权**：应用权限使用稳定的业务模块编码，例如 `system`、`settings`、`adapters`、`users`；授予模块后可调用该模块下全部已开放接口。具体路由操作仍由服务端映射并用于校验与审计，默认拒绝未登记的路径。
4. **模块范围清晰**：管理员按业务需要勾选模块。模块授权包含其中的读取、创建、修改、删除和执行等操作。确需全权时可显式授予 `*`；`*` 不包含应用管理、管理员认证/安全控制面或自定义 OpenAPI 脚本本身的调用。
5. **不可借道提权**：应用不能调用管理员登录、创建/修改其他应用或授予权限的控制面能力；不能借接口操作绕过该限制。
6. **兼容现状**：本能力不改变自定义 OpenAPI、插件 Web API 和后台管理员 Cookie/CSRF 鉴权语义。

## 3. 整体架构

```text
管理员后台
  └─ 应用管理 API ── 应用服务 / 密钥服务 / 权限目录
                              │
外部调用方                    │
  ├─ 开发者 HTTP API ── 认证 ─┤
  └─ MCP Streamable HTTP ─ 认证┤
                              ↓
                   统一授权与审计中间层
                              ↓
                    管理业务能力服务层
                              ↓
             config / plugin / payment / updater 等
```

两种协议不得各自实现一套业务逻辑，也不得通过 HTTP 内部请求模拟已登录管理员。公共服务层接收已验证的应用身份、权限上下文和请求上下文，完成权限判定后调用现有模块或抽取出的业务服务。

建议代码边界：

| 层 | 建议职责/位置 |
|---|---|
| 持久化 | `core/config` 与 `sqls/`：应用、凭证摘要、权限、审计数据和迁移 |
| 应用服务 | `core/application/` 或同等独立包：创建、查询、更新权限、轮换密钥、禁用/删除 |
| 模块目录与授权 | 服务端维护模块权限目录及路由能力映射：校验模块授权、过滤可见能力 |
| 业务服务 | `core/` 现有业务包：由后台 Handler 和外部协议共同调用；必要时逐步抽离 Handler 中的业务逻辑 |
| HTTP 协议 | `core/web/`：开发者 API 路由及统一 JSON 错误格式 |
| MCP 协议 | `core/mcp/` 或等价包：MCP Streamable HTTP transport、工具发现和工具调用 |
| 后台管理 | `core/web/` 管理 API；`web-ui/src/` 应用列表、权限编辑和密钥重置交互 |

目录为建议，实施时遵循仓库已有包依赖方向，避免 `config` 反向依赖 `web` 或 MCP 包。

## 4. 应用及凭证模型

### 4.1 应用字段

| 字段 | 说明 |
|---|---|
| `id` | 内部主键，服务端生成，不作为凭证 |
| `name` | 管理员填写的应用名称，必填，限制长度并去除首尾空格 |
| `client_id` | 服务端生成、唯一、可公开传输的应用标识；创建后不可编辑 |
| `client_secret_hash` | 当前 Secret 的单向摘要；不保存明文 |
| `permissions` | 已授予的模块编码集合；服务端校验目录中的有效模块 |
| `status` | `active` 或 `deleted`；删除后立即拒绝认证，删除为终态 |
| `created_at` / `updated_at` | 创建和更新时间 |
| `last_used_at` | 最近一次认证成功时间，可为空 |
| `deleted_at` | 软删除标记；删除立即撤销应用与其令牌 |

权限建议以关联表保存，便于唯一约束、索引和权限差异审计；如实现阶段采用 JSON，必须保留严格 schema 校验及原子更新语义。

### 4.2 appKey 与 appSecret

- 两者均使用 `crypto/rand` 等密码学安全随机源生成；`appKey` 不含权限信息。
- 管理后台字段名为 `appKey` / `appSecret`；外部认证协议字段名为 `app_key` / `app_secret`，分别对应同一应用 Key 与 Secret。
- `appSecret` 创建或重置时只完整展示一次。之后列表和详情永不返回明文或 Secret 片段。
- 数据库存储 Secret 的带盐慢哈希或经审查的专用凭证摘要，不记录到应用日志、调用日志、审计日志或错误信息。
- 重置 Secret 原子地递增 `credential_version` 并立即使旧 Secret 和已有访问令牌失效，不提供默认并行宽限期。
- 删除应用是终态逻辑删除，保留必要审计记录；不提供恢复入口。应用名、appKey、权限变化、重置和删除均记录操作者与时间。

### 4.3 应用访问令牌

REST 开放 API 使用单独的应用令牌，不直接接受 `appSecret`：

```http
POST /api/v1/open-api/token
Content-Type: application/json

{"app_key":"...","app_secret":"..."}
```

成功响应返回 `access_token` 和 `expires_in: 86400`。调用 REST 时使用 `Authorization: Bearer <access_token>`。REST 不接受 Basic，不接受把 `app_secret` 直接作为 Bearer token，也不接受管理员面板登录令牌。完全不带 Authorization 或带 Basic 时返回 `401 {"error":"缺少授权令牌"}`；把 `app_secret` 当 Bearer token 或使用无效/过期应用令牌时返回 `401 {"error":"令牌无效或已过期"}`。应用令牌只能代表签发它的应用，不能超出该应用当前权限。

应用令牌有效期固定为 24 小时。令牌应通过服务端签名密钥签发，并包含应用 ID、凭证版本、签发/过期时间和唯一请求关联 ID；每次请求校验签名、过期时间、应用状态和凭证版本，并读取当前权限集合。重置 `appSecret` 或删除应用会立即使相关令牌失效；撤销某个模块权限会立即禁止该模块后续调用。令牌不得放入 URL、Query、普通业务请求体、日志或错误信息。

## 5. 权限目录

应用权限以模块编码表示，如 `plugins`、`users`。服务端维护模块授权目录，供管理员后台读取和选择；服务端内部仍维护具体路由操作目录，用于将已授权模块映射到已开放接口、执行逐路由校验并记录操作审计。前端不自行定义模块权限语义。

至少覆盖以下管理员后台领域。表中操作是模块内可开放的接口范围，不作为管理员逐项勾选的权限：

| 领域 | 建议覆盖的能力范围 |
|---|---|
| 系统与设置 | 查看状态；读取和修改一般系统配置；更新、重启等高影响系统操作单独授权 |
| 适配器 | 列表/详情、创建/修改/启停/删除、置顶及平台配置相关操作 |
| 用户与账号 | 查询用户、账号及关联关系；修改用户资料或积分等现有后台动作 |
| 关键字回复 | 查询、创建、修改、启停、置顶和删除 |
| 插件 | 查询、创建/导入、配置、文件/代码、启停、删除、导出及访问控制等后台已有动作 |
| 插件 Web、脚本和运行环境 | 面板调用、任务/任务日志操作、环境变量、依赖和运行环境配置；执行/停止等动作单独授权 |
| 定时任务 | 查询、创建、修改、启停、立即执行和删除 |
| 支付与积分 | 支付设置、订单查询/操作、账单或退款相关现有动作、积分调整；资金及积分写操作单独授权 |
| 数据管理 | 表/视图查询、导出、导入和数据变更；导入、删除等破坏性动作单独授权 |
| 备份 | 列表、创建、下载、删除、恢复；恢复单独授权并记录审计 |
| 日志与统计 | 查看统计、查询/下载日志、清理与保留策略配置分别授权 |
| SDK 与参考信息 | 读取 SDK 文件和接口参考信息 |
| 自定义 OpenAPI 管理 | 查询/修改其配置、启停等管理动作可纳入 `open_apis` 模块；这不代表授予脚本调用权限或替换其 Token 机制 |

路由能力映射应以代码中的全部后台业务路由和操作为盘点基准，避免只覆盖页面主列表而漏掉详情、导入导出、文件操作、任务执行等子操作。后台新增管理功能时，必须同步将路由归入模块，并确认两种外部协议的可见性。

权限处理规则：

- 所有权限默认拒绝；无效、未知或已废弃权限在保存时拒绝，不静默放宽。
- 一个操作由服务端业务入口做权限判断；不能只在 Vue 页面隐藏按钮。
- 读权限和写权限分离；执行、删除、导入/恢复、更新/重启、资金/积分修改等高影响操作有独立授权。
- MCP 的工具列表只公布应用获授模块中已开放的能力；每次调用仍须校验目标路由和操作已登记，不能依赖“没列出来”作为安全措施。
- 权限变更立即影响后续调用，不等待 access token 自然过期。
- 应用不能授予自己权限；应用管理、管理员认证与安全控制面操作不作为普通业务能力开放，防止应用提权或接管管理员身份。
- `*` 全部模块权限是显式选择，仅由管理员后台授予；它覆盖所有已启用的业务模块（包括自定义 OpenAPI 配置管理），不覆盖应用管理、管理员认证与安全控制面，也不使应用能够调用自定义 OpenAPI 脚本端点。列表必须明确显示其高风险含义。

## 6. 统一业务服务层

将能力按业务域组织为服务方法，而不是将现有后台路由原样暴露。例如适配器管理由适配器服务提供列表、详情、更新和启停；插件、用户、支付、数据、备份等按域提供同等服务。

每个服务方法应定义：

1. 输入/输出结构、分页与过滤规则、字段白名单和最大请求体。
2. 必需的业务模块权限编码。
3. 参数校验、业务约束、幂等性要求及可取消的请求上下文。
4. 审计事件类别、结果和敏感字段遮蔽规则。
5. 对应后台操作与开发者 API/MCP 的一致性要求。

现有 `core/web` Handler 逐步改为“解析请求 -> 调用业务服务 -> 编码响应”。首期不要求一次性重构全部后台，但每个被外部开放的功能都必须落在可由两个协议复用的业务服务入口，不能在 HTTP/MCP Handler 中复制现有业务规则。

## 7. 开发者 HTTP API

统一前缀使用 `/api/v1/`，与 `/api/open/` 下现有用户自定义脚本 OpenAPI 及支付/回调等路径分开。这里的 `/api/v1/open-api/token` 是本规划的应用令牌端点，不是 `openapis/` 自定义脚本系统。

首期基础端点：

| 方法与路径 | 用途 |
|---|---|
| `POST /api/v1/open-api/token` | 使用 JSON `app_key` / `app_secret` 换取 24 小时应用令牌 |
| `GET /api/v1/capabilities` | 查询可用能力目录；应用身份只看到已授权能力 |
| `/api/v1/...` | 按业务域提供资源与动作接口，调用公共服务层；除 MCP 和 token 外均只接受应用 Bearer 令牌 |

API 应采用一致 JSON 外层、分页格式、字段命名、时间格式和错误结构；状态码区分未认证、无权限、参数无效、资源不存在、冲突、限流和服务端错误。每个端点必须在 API 文档中标注所需权限编码和副作用。

## 8. MCP 接口

- MCP 使用标准 MCP Streamable HTTP transport，HTTP 地址为面板地址后加 `/api/v1/mcp`，例如 `http://192.168.1.10:5700/api/v1/mcp`；协议包只做 transport、JSON-RPC 和 MCP 类型转换。
- MCP 与 REST 的鉴权入口不同，调用方不能混用：

| 入口 | 接受的 Authorization | 不接受 |
|---|---|---|
| MCP `/api/v1/mcp` | `Basic base64(app_key:app_secret)`；应用 Bearer 令牌；面板登录 Bearer 令牌 | URL/Query 中的凭证 |
| REST `/api/v1/...`（token 端点除外） | 仅 `/api/v1/open-api/token` 签发的应用 Bearer 令牌 | Basic、直接把 `app_secret` 当 Bearer、面板登录令牌 |

- MCP 应用鉴权可直接用 `Authorization: Basic <base64(app_key:app_secret)>`，也可用 `Authorization: Bearer <令牌>` 携带 `/api/v1/open-api/token` 签发的应用令牌。面板登录令牌仅作为 MCP 兼容方式；它代表管理员会话而非应用身份，按管理员身份授权和审计，不受应用权限集合约束。应用凭据方式是推荐方式。
- Basic 只允许用于 MCP 入口，REST 端点一律拒绝 Basic。任何方式都不得把 Secret 或令牌放进 URL/Query。生产部署必须使用 HTTPS；局域网 HTTP 示例仅用于受信任网络的联调。
- MCP 的 Basic 与 Bearer 认证成功后都解析为统一调用主体：应用凭据/应用令牌对应应用主体，面板登录令牌对应管理员主体。工具列表与每次工具调用均依据主体权限过滤和授权；工具未列出不能代替服务端授权检查。
- 按 capability registry 生成确定排序的工具清单；工具名称稳定，描述、参数 JSON Schema、权限要求和副作用均从服务定义生成或校验。
- `tools/call` 路由到与 HTTP API 相同的业务服务方法及授权器；禁止为 MCP 单独开后门或更宽权限。
- MCP 工具的返回内容应结构化、便于机器读取；对错误区分协议错误与业务失败，并确保不泄露内部堆栈、凭证和敏感配置。
- 首期优先实现远程 Streamable HTTP；不因 MCP 协议支持而自动增加本地 stdio 服务或新的后台能力。
- 具体协议版本、SDK、HTTP 头要求及互操作性测试应在实施时根据官方 MCP 当前规范和 Go SDK 状态锁定，并把版本写入依赖与兼容性说明。

## 9. 管理员后台应用管理

新增“开发者应用”管理页，后台仅管理员会话可进入，并使用现有 CSRF 保护。

### 9.1 列表

列表字段：名称、`appKey`、权限摘要、状态、创建时间、最近使用时间、操作。`appSecret` 永不在列表显示。

操作：

- **创建应用**：填写名称并选择模块；提交后生成 `appKey` 和 `appSecret`。Secret 仅在创建成功弹窗显示一次，提供复制动作，并提示离开后不可再次查看。
- **修改权限**：显示业务模块目录，每个模块授权其全部已开放接口；保存立即生效。
- **重置 appSecret**：二次确认后立即撤销旧 Secret 和相关 token；新 Secret 只显示一次。
- **删除应用**：二次确认并明确说明所有凭证立即失效且不能恢复；执行软删除并保留审计记录。

名称编辑可由详情/编辑入口完成，不改变 `appKey`。除上述操作外，不添加与需求无关的应用开关或生命周期状态；如系统需要管理员暂时停用应用，可由后续需求决定是否增加独立操作。

### 9.2 管理 API

后台管理 API 与外部开发者 API 分离，例如 `/api/developer-apps`，只允许管理员身份：列表、能力目录、创建、修改名称/权限、重置 Secret 和删除。创建/重置响应可以包含一次性明文 Secret，其它响应结构不得包含明文或摘要。

## 10. 安全、审计与可用性

- 应用凭证交换、REST 和 MCP 生产调用要求 HTTPS；应用凭证交换与业务 API 应应用独立限流、请求体上限、并发和超时限制。
- 对比 Secret/令牌时采用恒定时间比较；token 签名算法、密钥轮换、过期时间和撤销语义有明确配置与测试。
- 对外错误不区分 appKey 是否存在；认证失败和权限拒绝不能泄露应用详情。
- 日志只记录应用内部 ID、能力编码、协议、请求 ID、来源地址、结果、耗时和必要的资源标识；对 Secret、token、密码、支付凭证及敏感用户字段统一脱敏。
- 建立独立应用调用审计记录：应用、能力、请求 ID、时间、来源、结果、耗时和必要的脱敏参数摘要。成功与拒绝都需记录；审计写入失败策略须定义，涉及破坏性操作时不能静默丢弃。
- 使用可信代理策略解析客户端地址，不盲信任任意 `X-Forwarded-For`。错误响应不携带内部堆栈。
- 分页、批量操作、导出和耗时任务都需要上限；危险写操作定义幂等键或冲突处理。
- MCP 和 HTTP 使用同一限流身份（应用）和业务审计标准；协议请求 ID 关联到内部 request ID。

## 11. 迁移与实施阶段

### 阶段 0：能力盘点与契约

- 盘点 `core/web/server.go` 注册的所有管理员业务路由、各 Handler 的操作分支及权限边界。
- 建立完整 capability registry 草案，逐项映射模块、动作、风险级别、业务服务入口及对应 HTTP/MCP 暴露情况。
- 定稿应用字段、凭证交换协议、错误格式、分页和审计字段。

### 阶段 1：应用和安全底座

- 新增数据库迁移与应用持久化方法。
- 实现应用创建、列举、更新权限、重置 Secret、删除、能力目录、凭证校验、短期 token 和统一授权器。
- 实现管理 API 及应用管理页。
- 增加密钥脱敏、撤销即时性、权限变更即时性、管理员/CSRF、防越权与审计验证。

### 阶段 2：公共业务能力

- 先接入低风险只读能力，验证后台/API 共用服务层的边界与响应契约。
- 按业务域逐步接入全部管理员后台业务能力；每域先补齐授权编码与服务入口，再接 HTTP 和 MCP。
- 高风险写操作应有审计和确认/幂等规则；模块授权仍覆盖模块内所有已开放操作。

### 阶段 3：开发者 HTTP API

- 完成 `/api/v1/open-api/token`、能力目录、版本化业务 API、对外接口说明和 SDK 示例。
- 对每个能力执行授权正反例、参数边界、限流、撤销和审计验证。

### 阶段 4：MCP

- 接入 Streamable HTTP transport。
- 从同一能力目录生成工具及输入 schema；调用统一服务层。
- 使用 MCP 官方 Inspector/兼容客户端完成初始化、工具枚举、授权过滤、合法/非法调用和错误互操作验证。

### 阶段 5：上线与运维

- 文档说明 HTTPS、凭证保管、最小权限、密钥轮换、代理配置、日志和备份恢复要求。
- 先以管理员手工创建的应用进行小范围验证，再逐业务域启用能力。
- 监控认证失败、权限拒绝、调用延迟、错误率、限流和撤销事件；提供审计查询与保留策略。

## 12. 验收标准

1. 管理员可创建应用，并获得唯一 `appKey` 与只展示一次的 `appSecret`。
2. 管理员可以按模块修改权限、重置 Secret 和删除应用；这些管理 API 受管理员会话与 CSRF 保护。
3. 数据库和任何日志中均找不到 Secret 明文；Secret 重置、应用删除和权限撤销都立即影响后续调用。
4. 模块权限目录覆盖管理员后台全部业务模块；获授模块后可调用其全部已开放接口，未登记路由仍默认拒绝。
5. HTTP 与 MCP 对相同应用使用相同凭证、权限判断、业务服务结果、限流身份和审计字段。
6. 通过某一协议获得的权限不能绕过另一协议共享的业务授权；未授权的 API 请求和 MCP 工具调用均被拒绝。
7. 后台和外部协议不共享管理员 Cookie/会话，不允许调用应用管理或管理员认证控制面来提权。
8. 自定义 OpenAPI 仍按原 `config.json` 和 Token 机制运行，与新应用体系互不隐式授权。
9. 管理员后台新增业务操作时有对应 capability、风险等级和授权测试；已开放能力有接口文档和可重复的正反向验证。

## 13. 需要实施时确认的产品细节

以下不阻碍本规划：默认 access token 有效期、签名密钥配置和轮换方式；审计保留天数与后台查询筛选；MCP 首期是否只支持无状态调用。实施前应结合部署形态、SQLite 当前迁移方式和 Go MCP SDK 兼容状态定值。阶段 1 交付应用与安全底座；全部管理员后台业务能力是最终覆盖目标，阶段 2 起按业务域逐步接入，只有 capability registry 与后台路由/操作清单完成逐项映射并通过验收后，才算达到全量覆盖。
